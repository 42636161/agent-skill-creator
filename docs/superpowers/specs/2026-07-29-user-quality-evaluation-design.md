## 评价维度与改进方向

### 维度 A：用户交互与对话体验

以 crm-reports-skill 为样本，站在对话系统中两个角色的角度分别审视技能质量：一是加载并执行技能的 agent（调用者 AI），二是与 agent 对话的最终用户。

#### A-a. 调用者 AI 视角

agent 是技能的"运行环境"——它读 SKILL.md 和 AGENTS.md，决定是否激活技能、执行流水线、解析输出、组织回答。从 agent 的立场看，技能的质量取决于它被设计得好不好"用"。

##### A-a-1. 激活触发词覆盖不足

**问题.** 当前触发词（"clean this CRM export"、"weekly sales report"）代表的是技能作者对技能的理解，不是用户的真实说法。用户会说"帮我看看这个表格"、"这周的数帮我整一下"、"I exported this from Salesforce"——这些表达不包含"CRM"或"report"关键词。agent 拿到这些输入时，无法判定是否应该激活技能。

**改进需求.** 触发词需覆盖用户真实的模糊表达（用户不知道这是"CRM 报告"）、半信息态（用户给了文件但没说清楚要什么）、以及多语言中常见的非术语说法。

##### A-a-2. 错误路径缺少诊断信息

**问题.** 当输入数据的列名不在技能支持的语言列表里（比如中文列名"区域"、"金额"），技能静默返回空报告而非报错。agent 拿到的是一个看似成功但内容为空的 JSON，既不知道发生了什么，也没有任何信息可以翻译给用户——只能硬着头皮说"报告已生成"或猜一个"数据可能有问题"。

**改进需求.** 技能在异常路径上应产出结构化诊断信息：哪些输入没能被处理、最接近的匹配是什么、agent 可以向用户提出什么修复建议。agent 需要的是可解读的错误信号，不是静默空值。

##### A-a-3. 激活过程对用户不透明

**问题.** agent 激活技能时，用户看不到信号。agent 开始输出结果，但用户不清楚这些结果是来自 agent 的基础知识、一个工具调用、还是一个已安装的技能。当结果出问题时，用户无法归因——是 agent 不行，还是技能不行？

**改进需求.** agent 在激活技能时需要一套轻量的透明度机制：在开始处理前向用户发出一个明确的"技能已激活"信号，让用户建立清晰的因果链。这个信号应该是技能定义的一部分，而非依赖 agent 自行判断。

##### A-a-4. Agent 执行指引过于隐式

**问题.** SKILL.md 中的 Usage / Pipeline 段落是给人看的 CLI 参考（"One command does everything: `python3 scripts/run_pipeline.py --input ... --output ...`"）。agent 需要自己从这些段落中推断出：用户说 X 时应执行 Y 命令，参数 Z 从哪里来，输出后应如何呈现。这种推断在不同 agent 平台上产生不同结果——有些 agent 能正确推理，有些则跑偏。

**改进需求.** 技能需要向 agent 提供一个结构化的"行为映射"：用户意图 → 应执行的命令/脚本 → 参数来源 → 输出处理规则。agent 不需要自己猜该做什么。

---

#### A-b. 最终用户视角

最终用户不关心技能怎么实现，不读 SKILL.md，不知道 JSON schema。ta 只跟 agent 说话，看到 agent 的回复。技能的"用户体验"就是 agent 回复的质量。

##### A-b-1. 输出呈现不一致且常不可用

**问题.** 技能产出 JSON，agent 负责翻译给人看。但 agent 没有被指引该怎么做——可能一句"report.json 已生成"了事，也可能罗列全部 JSON 字段。用户在不同平台上得到完全不同的体验，且大概率不是最优的。

**改进需求.** 技能需要约束 agent 的输出呈现行为：哪些指标该先说、以什么形式（表格/段落/列表）、在什么场景下主动对比或追问。这不是让所有 agent 说一模一样的话，而是保证用户在任意平台上都能得到有用且结构清晰的回答。

##### A-b-2. 配置项对用户不可见

**问题.** 技能有多个可调参数（去重开关、日期格式、异常值阈值、缺失值填充等），但它们只在 `assets/config.json` 中存在。用户在对话中永远不会问"异常值阈值能调吗"——因为 ta 不知道有这个选项。如果默认参数不适合 ta 的数据，ta 的判断是"这个技能不好用"，而非"参数需要调"。

**改进需求.** 技能需在对话层面暴露可配置性：让 agent 知道有哪些可调项、默认值是多少、什么情况下应主动向用户提议调整。参数应翻译成用户能理解的语言（"异常值敏感度"而非 "outlier_std_threshold"）。

##### A-b-3. 缺少预览确认模式

**问题.** 流水线是一次性操作：读取 → 清洗 → 分析 → 输出。用户无法在清洗步骤执行前预览——ta 不知道会被删掉哪些重复行、哪些值会被标记为异常、日期会被改成什么格式。如果清洗结果不对，用户只能拿到最终报告才知道。

**改进需求.** 技能应让用户能在执行前预览变更计划：哪些行受影响、如何影响、清洗后的预估结果。用户确认后再执行。这需要在流水线层面支持增量或分步操作。

##### A-b-4. 不支持对比和历史

**问题.** 技能每次运行都是独立事件。用户每周跑一次报告，但每次都从零开始——没有上周数据的对比，没有趋势，没有变化幅度。用户拿到孤立数字（"总销售额 ¥92,400"），而 ta 真正想知道的是"跟上周比怎么样"。

**改进需求.** 技能应支持与历史报告的对比：接受基线数据，在输出中追加对比维度（变化量、变化率、按维度的增减排名）。

##### A-b-5. 输入格式限制与现实脱节

**问题.** 技能只支持 CSV。实际 CRM 系统导出经常是 XLSX、XLS 或 TSV。用户交过来一个 Excel 文件，agent 要么放弃，要么需要额外写代码转换——增加了失败概率和交互轮次。

**改进需求.** 技能应在入口处处理常见格式差异：自动检测文件类型并转换，让用户不需要关心格式问题。转换失败时应有清晰的边界提示。

##### A-b-6. 功能发现完全被动

**问题.** 技能有多个维度的分析能力（按区域、按产品、按销售代表、按客户群），但用户只在第一次使用后才知道。如果用户只说了"帮我整理这个表格"，ta 可能永远不知道技能还能按产品销售代表分组——除非 ta 恰好说到了。功能发现完全依赖用户主动猜测。

**改进需求.** 技能的回答中应包含轻量的功能暗示：在呈现完本次请求的结果后，agent 主动提及一项相关但未请求的能力（"另外，这份数据还可以按销售代表分组——需要我看一下吗？"），让用户逐渐建立对技能能力边界的认知。
